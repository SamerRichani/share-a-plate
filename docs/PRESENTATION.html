ShareAPlate

A full-stack web app (React + Express + PostgreSQL) that lets restaurants and shops give leftover food to people and charities nearby, instead of throwing it away.

The professor's brief asks for 5–8 minutes covering: the problem, a live walkthrough, one technical challenge, and what you'd build next. This plan runs 8 minutes. Then comes Q&A.

Presenter 3 · and for the professor's questions

Code tour: the 6 files to know

If the professor asks "show me how X works", open these. Each one is short and commented.

backend/src/app.js

Builds the server: security headers → JSON body (max 100 KB) → rate limits → the four route groups → error handler. In production it also serves the built React site.

backend/src/routes/offers.js

The URL list. Each line says the HTTP verb, the URL, who's allowed, and which function runs.

router.use(authenticate);                       // must be signed in
router.post('/', authorize('donor'), createOffer); // only donors
backend/src/middleware/auth.js

authenticate reads the Authorization: Bearer … header, verifies the JWT signature and expiry, then loads the user (and role) from the database. authorize('donor') returns 403 if the role doesn't match.

backend/src/controllers/reservations.js → createReservation

The "last portion" challenge. Everything runs inside withTransaction, and the offer row is locked:

SELECT * FROM offers WHERE id = $1 FOR UPDATE   -- lock
... check portions left ...
INSERT INTO reservations ...                       -- with a random pickup code
UPDATE offers SET remaining_quantity = remaining_quantity - $1
COMMIT                                             -- or ROLLBACK if anything failed
frontend/src/services/api.js

Every request from React goes through request(): adds the token header, sends JSON to /api…, turns errors into readable messages, and signs you out on a 401.

frontend/src/app/App.jsx

Client-side routing with React Router. RequireAuth sends visitors to /login; RoleRoute hides pages for other roles. These are for convenience only: the server re-checks everything.

Questions about the code

Professor Q&A

EasyWhat is a REST API, and what makes yours RESTful?

The server exposes resources at URLs (/api/offers, /api/reservations) and uses HTTP verbs for actions: GET reads, POST creates, PATCH updates, DELETE removes. Data goes back and forth as JSON, and status codes say what happened.

EasyWhat status codes do you use?

200 OK · 201 created · 400 bad input · 401 not signed in / bad token · 403 signed in but not allowed · 404 not found · 409 conflict (e.g. not enough portions) · 413 body too big · 429 too many requests · 500 unexpected server error.

EasyWhat is middleware?

A function that runs before the route's main code, and can stop the request or pass it on with next(). Ours: securityHeaders, rateLimit, express.json, authenticate, authorize, and the error handler at the end.

backend/src/middleware/

EasyHow does the React app talk to the server?

Through fetch in services/api.js. During development, Vite's proxy forwards /api calls from port 5173 to Express on 5001. In production, Express serves the website and the API from the same address.

EasyWhat is a protected route?

On the frontend: pages wrapped in RequireAuth/RoleRoute redirect you if you're not signed in or have the wrong role. On the backend: routes behind authenticate + authorize(role). The backend one is the real protection.

EasyWhy PostgreSQL and not MongoDB?

Our data is relational: users have offers, offers have reservations and reports. PostgreSQL gives us foreign keys, CHECK constraints (e.g. quantity > 0) and transactions with row locks, which we need for reservations.

EasyWhat are components and state in your app?

Components are reusable UI pieces (OfferCard, Button, TextField, SiteHeader). State is data that changes the screen, held with useState (e.g. the filters, the list of offers, loading/error). Signed-in user state is shared app-wide with React Context (AuthContext).

EasyWhat is a migration and a seed?

A migration is a numbered SQL file that creates or changes tables (db/migrations/001_initial_schema.sql); we record which ones have run. A seed fills the database with demo accounts and offers (db/seed.js).

HardWalk me through what happens when a recipient clicks "Reserve food".

1. React calls api.post('/offers/5/reservations', {quantity: 2}) with the token. 2. Express: security headers → rate limit → express.json. 3. authenticate verifies the JWT, loads the user. 4. authorize('recipient'). 5. validateIdParam checks 5. 6. createReservation validates quantity, opens a transaction, locks the offer row, checks it's active / enough portions / no duplicate reservation, inserts the reservation with a random code, lowers remaining_quantity, commits. 7. Replies 201 with the reservation; React shows the code.

HardHow do you prevent a race condition on the last portion?

Transaction + SELECT … FOR UPDATE. The first request locks the offer row; the second waits until the first commits, then reads the updated remaining quantity and gets 409 "Not enough portions remain". The database also has a CHECK so remaining_quantity can never go below 0. We always lock the offer before the reservation, in every function, so two requests can't deadlock.

HardWhy JWT instead of server sessions? Where is it stored and why?

JWT is stateless: the server doesn't keep a session table, it just checks the signature. It contains only the user id and expiry (1 hour). On the browser we keep it in sessionStorage so a refresh keeps you signed in, and closing the tab signs you out. Trade-off: an XSS bug could read sessionStorage; we reduce that risk with React's escaping and a strict CSP. An httpOnly cookie would hide it from JavaScript but then we'd need CSRF protection; it's a reasonable next step.

HardWhy read the role from the database instead of putting it in the token?

So a role change or a deleted account takes effect immediately, and so the token holds nothing an attacker would want to change. Cost: one small query per request, using the primary key.

HardWhy "removed" instead of deleting offers?

Soft delete keeps history: reservations and reports point to the offer (foreign keys). Removing cancels pending reservations and returns their portions, but collected ones stay as a record.

HardHow is the useEffect in OffersPage cleaned up?

It creates an AbortController and returns () => controller.abort(). If filters change or you leave the page before the request finishes, the old request is cancelled so it can't overwrite newer results.

HardHow do pagination and filters work in SQL?

LIMIT/OFFSET from ?page=&limit= (limit capped at 100). Filters add WHERE conditions, but the values always go in as $1, $2…; only column names from our own fixed list are written into the SQL text.

HardWhat do your tests cover and how do they run?

Backend: Node's built-in test runner starts the real Express app on a random port and sends real HTTP requests: forged token, alg:none token, admin sign-up attempt, broken JSON, huge body, security headers, rate limit (13 tests). Frontend: Vitest + Testing Library render components in a fake browser (jsdom): offer card, XSS text, redirect to sign-in (6 tests). npm test runs both.

HardHow is it deployed?

One Node web service: npm run build builds React into frontend/dist; npm run start:prod runs migrations and starts Express, which serves the site and the API. A hosted PostgreSQL connects with DATABASE_URL over SSL. Secrets are environment variables on the host. See docs/DEPLOYMENT.md.

Honest limits (say these if pushed)

Signing out doesn't kill the token on the server.A stolen token works until it expires (max 1 hour). Fix: short tokens + refresh tokens, or a revocation list.
Rate limit is per IP and in memory.A botnet with many IPs could guess slowly; restarting the server resets counts. Fix: per-account lockout, Redis-backed limits, CAPTCHA after failures.
No email verification or password reset yet.Someone could sign up with a fake email. Fix: verification emails (planned with the email feature).
Token in sessionStorage.Readable by JavaScript if an XSS ever got through. Mitigated by React + CSP; an httpOnly cookie would be stronger.
Admin has no two-factor login.Next step for the most powerful account.

The morning of

Before you start

  1. In the project folder: npm run db:seed --prefix backend (fresh demo offers)
  2. npm start → wait for "API running" → open http://localhost:5173
  3. Run npm test once, so you know it's green before showing it
  4. If you use the live URL: open it a minute early (free hosts sleep)
  5. Zoom the browser to ~125% so the room can read it
  6. Have these files open in the editor: routes/offers.js, controllers/reservations.js, middleware/auth.js
  7. If a sign-in says "Too many attempts": stop and restart npm start (resets the counter)

Cheat sheet

Glossary

Frontend / Backend
The website in the browser / the server and database behind it.
API, REST
The list of URLs the website can call; REST = resources + HTTP verbs + JSON.
Middleware
Code that runs before a route and can stop the request.
JWT
A signed "pass" proving who you are; expires after 1 hour.
Hashing (bcrypt)
One-way scrambling of passwords; slow on purpose.
Transaction
Several database changes that all succeed or all get undone.
Row lock (FOR UPDATE)
Makes other requests wait until we finish changing that row.
Rate limiting
Max requests per visitor per time window.
CSP
Content-Security-Policy: tells the browser which sources it may load scripts from.
IDOR
Changing an id in the URL to reach someone else's data.
Migration / Seed
SQL that creates tables / script that adds demo data.
Soft delete
Marking a row "removed" instead of erasing it, to keep history.
