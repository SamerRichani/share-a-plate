ShareAPlate

A full-stack web app where restaurants and shops post leftover food, and people or charities nearby reserve it and pick it up with a code. Built with React, Express and PostgreSQL.

How to use this page. When the professor asks "how did you do X?", go to section 10: each feature is a numbered trail of file:line stops from the button the user clicks down to the database. Open those files in the editor and walk through them in order.

Before you start (morning of)

Setup

How to run the project

First time

Needs Node.js 20+ and PostgreSQL with a shareaplate database and shareaplate_app user.

npm run setup

Creates backend/.env with a random JWT_SECRET (backend/scripts/create-env.js), installs both halves, runs migrations, seeds demo data. If the database step fails, put your password in PGPASSWORD in backend/.env and run again.

Every time

npm start

start.js runs both: backend on :5001 (node --watch, restarts on save) and frontend on :5173 (Vite). Ctrl + C stops both. Port 5001, not 5000, because macOS AirPlay uses 5000.

Tests

npm test

Backend: node --test. Frontend: vitest run.

Production / deploy

npm run build
npm run start:prod

Build makes frontend/dist; start:prod runs migrations and starts Express, which serves both the site and /api. Env vars: DATABASE_URL, JWT_SECRET, TRUST_PROXY=1.

If something goes wrong

MessageFix
"Port 5001 is already in use"Another copy is running. Stop it with Ctrl + C in its terminal, then npm start.
"Too many sign-in attempts"Rate limit (20 per 15 min). Restart npm start to reset.
"Startup failed: password authentication failed"Wrong PGPASSWORD in backend/.env.
"JWT_SECRET must contain at least 32 bytes"Run node backend/scripts/create-env.js (only if .env is missing) or set it manually.
"Pickup requires … within its collection window"The offer's pickup time hasn't started or has ended. Re-seed, or create an offer whose pickup starts now.

User guide

How to use the website

On the sign-in page, the Donor demo / Recipient demo / Admin demo buttons fill in the demo accounts. They only exist when running locally, never on the deployed site.

🧑‍🍳 Donor

  1. My offers → Create an offer: title, description, food type, area, pickup address, portions, pickup start and deadline.
  2. Each card has Reservations, Edit, Close (no new reservations), Remove (cancels pending ones).
  3. Reservations page: type the recipient's code → Confirm pickup.

🙋 Recipient

  1. Find food: filter by area, food type, pickup time.
  2. Open an offer → choose portions → Reserve food → a 6-character pickup code appears.
  3. My reservations: see codes, cancel before the deadline.
  4. Report this offer if something's wrong.

🛡️ Administrator

  1. Moderation → Reports tab: filter by status, Resolve or Dismiss.
  2. Offers tab: every offer of every donor; Close or Remove offer.
  3. Admins can't sign up; accounts are created by the seed script.

The life of one request

securityHeaders→express.json (100 KB)→rateLimit→router→authenticate→authorize(role)→validateIdParam→controller→database→JSON reply

Errors at any step are thrown with httpError(status, message) and turned into JSON by the error handler at the end of app.js.

Development

Two servers: Vite on :5173 serves React and proxies /api to Express on :5001 (frontend/vite.config.js). Same origin from the browser's view, so no CORS needed.

Production

One server: Express serves the built React files from frontend/dist and the API at /api (app.js lines 42–52). Hosted PostgreSQL via DATABASE_URL over SSL.

PostgreSQL

Database

Defined in backend/db/migrations/001_initial_schema.sql. The database enforces rules too, as a second safety net behind the API.

users

  • idPK, identity
  • namenot blank
  • emailUNIQUE, lowercase
  • password_hashbcrypt
  • roledonor | recipient | administrator
  • created_attimestamptz

CHECK on role values; email must be trimmed and lowercase.

offers

  • idPK
  • donor_idFK → users
  • title, descriptiontext
  • category, arealowercase
  • locationpickup address
  • quantity> 0
  • remaining_quantity0 … quantity
  • pickup_start, pickup_deadlinedeadline > start
  • statusactive | closed | removed

Partial index for browsing active offers by area, category, deadline.

reservations

  • idPK
  • offer_idFK → offers
  • recipient_idFK → users
  • quantity> 0
  • pickup_codeUNIQUE
  • statusreserved | collected | cancelled | expired

Unique partial index: only one pending reservation per recipient per offer.

reports

  • idPK
  • reporter_idFK → users
  • offer_idFK → offers
  • reasonnot blank
  • statusopen | resolved | dismissed

Foreign keys don't cascade: history is never silently deleted.

Relationships

One user (donor) has many offers. One offer has many reservations and many reports. One user (recipient) has many reservations. One user can file many reports.

Status lifecycles

Offer: active→closed (no new reservations) →removed (soft delete)
Reservation: reserved→collected or cancelled or expired (after deadline)
Report: open→resolved or dismissed

Migrations

db/migrate.js creates a schema_migrations table, runs every .sql file in migrations/ in order once, inside a transaction, and records its name. To change the schema, add 002_….sql; never edit an applied file.

Seed

db/seed.js creates or updates the 3 demo accounts from .env (seedUser, line 63) and 5 demo offers (seedDemoOffers, line 96). Pickup windows open 1 hour before seeding; re-seeding refreshes them.

Express

Backend, file by file

src/server.js

Loads .env, checks the database with SELECT 1, starts listening on PORT, explains a busy port, closes the server and DB pool on Ctrl+C.

src/app.js

The middleware order: security headers (18) → JSON body ≤100 KB (21) → rate limits (25–30) → 4 routers (33–36) → API 404 (39) → serve built website (42–52) → error handler (55).

src/config/db.js

PostgreSQL connection pool (max 10). withTransaction(work) (23): BEGIN → work → COMMIT, or ROLLBACK on any error, always releases the connection.

src/config/auth.js

Reads JWT_SECRET; refuses to start if it's missing or under 32 bytes.

src/middleware/auth.js

authenticate (11): Bearer token → jwt.verify (HS256 only) → load user from DB → req.user. authorize(...roles) (39): 403 if role not allowed.

src/middleware/security.js

securityHeaders (4): CSP, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy, HSTS on HTTPS. rateLimit (25): per-IP counter in a Map, 429 + Retry-After.

src/routes/*.js

URL → role → controller. router.use(authenticate) protects the whole file; router.param('id', validateIdParam) checks every :id.

src/controllers/auth.js

register (34), login (67), getMe (89). bcrypt cost 12, FAKE_HASH for constant timing, createToken (24), publicUser never returns the hash.

src/controllers/offers.js

cleanOfferData (12) validates fields; listOffers (41) with filters + pagination; getOffer (92) with visibility rules; createOffer (108); changeOffer (126) lock + ownership; updateOffer (143); removeOffer (191); moderateOffer (219).

src/controllers/reservations.js

makePickupCode (13); createReservation (20) the locked transaction; listReservations (55); changeReservation (82) lock order; cancelReservation (94); confirmPickup (111).

src/controllers/reports.js

createReport (8): inserts only if the offer exists (INSERT … SELECT).

src/controllers/admin.js

listReports (12), listOffers (28) with status filter; updateReport (44): only an open report can change.

src/utils/httpError.js

Throws an Error with a status; the error handler sends it as JSON.

src/utils/validation.js

isPositiveInteger, isNonEmptyString, isEmail, allowOnlyFields (24, blocks mass assignment), validateIdParam (32), readPagination (41, limit ≤ 100), parseTimestamp (51).

test/*.test.js

Start the real app on a random port and send real HTTP requests (no database needed for these).

"How did you do this feature?"

How we built each feature

Each trail goes from what the user clicks, through the API, to the database. Line numbers are where the function starts. Paths start at frontend/src/ or backend/src/.

Sign up

POST /api/auth/register
  1. Frontendpages/RegisterPage.jsx:26 submit

    Controlled form (name, email, password, donor/recipient). Calls register(values) from the auth context.

  2. Frontendcontext/AuthContext.jsx:63 register

    api.post('/auth/register'), then stores the token (setAccessToken) and user (setUser).

  3. Backendroutes/auth.js:6 → controllers/auth.js:34 register

    Validates: name ≤ 100, email shape, password 12+ chars (≤ 72 bytes), role must be donor or recipient. Hashes with bcrypt.hash(password, 12).

  4. DatabaseINSERT … ON CONFLICT (email) DO NOTHING RETURNING …

    If no row comes back, the email exists → 409. Otherwise → 201 with a token from createToken (line 24) and the public user.

Sign in

POST /api/auth/login
  1. Frontendpages/LoginPage.jsx:37 submit

    Calls login(values), then navigates to the page you came from (location.state.from) or /offers.

  2. Frontendcontext/AuthContext.jsx:52 login

    Posts credentials; saves token and user.

  3. Backendapp.js:29 loginLimit → controllers/auth.js:67 login

    Max 20 attempts / 15 min per IP. Finds user by lowercase email, runs bcrypt.compare (with FAKE_HASH if the email doesn't exist, so timing is equal). Same message for both failures → 401.

  4. Backendcontrollers/auth.js:24 createToken

    jwt.sign({}, secret, { algorithm: 'HS256', subject: user.id, expiresIn: '1h' }).

Protected routes & roles

every request
  1. Frontendapp/App.jsx:24 RequireAuth · :35 RoleRoute

    Redirect to /login if signed out, to /offers if wrong role. This is UX only.

  2. Frontendservices/api.js:40 request

    Adds Authorization: Bearer <token> to every call.

  3. Backendmiddleware/auth.js:11 authenticate

    Parses the header with a regex, jwt.verify(token, secret, { algorithms: ['HS256'] }), checks sub is a positive integer and exp exists, loads id, name, email, role from the DB → req.user. Any failure → 401.

  4. Backendmiddleware/auth.js:39 authorize(...roles)

    Used in routes, e.g. routes/offers.js:21 authorize('donor'). Wrong role → 403.

Stay signed in after refresh / session expiry

frontend
  1. Frontendservices/api.js:8 readStoredToken · :30 setAccessToken

    Token saved in sessionStorage; read back when the page loads. Wrapped in try/catch in case storage is blocked.

  2. Frontendcontext/AuthContext.jsx:12 readStoredUser

    Restores the user only if a token also exists. useState(readStoredUser) = lazy initial state.

  3. Frontendservices/api.js:71 → AuthContext.jsx:35

    On a 401, the token is cleared and a shareaplate:session-expired window event fires; the context listens, signs out and shows "Your session expired".

Browse & filter offers, pagination

GET /api/offers
  1. Frontendpages/OffersPage.jsx:67 applyFilters · :30 useEffect

    Form state is separate from applied filters. The effect builds URLSearchParams (page, limit=12, area, category, pickup_from/to as ISO) and refetches when applied or page change; cleanup aborts the old request.

  2. Frontendcomponents/Pagination.jsx

    "Next" is enabled when a full page came back (offers.length === limit).

  3. Backendcontrollers/offers.js:41 listOffers

    Builds a conditions[] list and a values[] list: public view = active, portions > 0, deadline in future. Each filter pushes a value and adds column = $n. Column names come from our fixed list only.

  4. Backendutils/validation.js:41 readPagination

    page ≥ 1, limit 1–100 → LIMIT $x OFFSET $y.

Create & edit an offer

POST / PATCH /api/offers
  1. Frontendcomponents/OfferForm.jsx:24 submit

    One form for create and edit. Checks deadline > start, converts datetime-local to ISO with timezone (utils/format.js fromDateTimeLocal), quantity to a number.

  2. Frontendpages/OfferFormPage.jsx:40 save

    editing prop decides: api.patch('/offers/:id') or api.post('/offers'). Edit mode first loads the offer (line 18).

  3. Backendcontrollers/offers.js:108 createOffer

    allowOnlyFields rejects unknown keys (e.g. donor_id), cleanOfferData (12) trims, lowercases area/category, checks lengths, quantity and dates. donor_id always comes from req.user.id, never the body.

  4. Backendcontrollers/offers.js:143 updateOffer

    Inside changeOffer (lock + owner check). Can't edit removed/expired offers; can't lower quantity below committed portions; can't move place/time once someone reserved. remaining = new quantity − committed.

Close / remove an offer

PATCH status / DELETE
  1. Frontendpages/MyOffersPage.jsx:47 changeStatus

    Confirm dialog, then api.delete (remove) or api.patch({ status: 'closed' }), then reload the list.

  2. Backendcontrollers/offers.js:126 changeOffer

    Transaction, SELECT … FOR UPDATE, 404 if missing, 403 if not owner (and not admin).

  3. Backendcontrollers/offers.js:191 removeOffer

    Soft delete: pending reservations → cancelled (or expired if past deadline), their portions added back, offer status → removed. Collected reservations stay as history.

Reserve portions (the technical challenge)

POST /api/offers/:id/reservations
  1. Frontendpages/OfferDetailPage.jsx:53 reserve

    Posts { quantity: Number(quantity) }, shows the returned code, refetches the offer to update portions left. The button only shows when canReserve is true.

  2. Backendroutes/offers.js:24 authorize('recipient')

    Only recipients.

  3. Backendcontrollers/reservations.js:20 createReservation

    Validates quantity, then withTransaction: SELECT * FROM offers WHERE id=$1 FOR UPDATE (row lock) → checks active, not expired, enough portions, no existing pending reservation → INSERT with makePickupCode() → remaining_quantity − quantity → COMMIT. Returns 201.

  4. Databaseconfig/db.js:23 withTransaction · schema CHECKs

    Concurrent requests wait on the lock and then see the updated count. CHECK remaining_quantity BETWEEN 0 AND quantity and the unique partial index are backups.

Pickup code & confirm pickup

POST /api/reservations/:id/pickup
  1. Backendcontrollers/reservations.js:13 makePickupCode

    6 characters from ABCDEFGHJKMNPQRSTUVWXYZ23456789 (no 0/O, 1/I/L) using crypto.randomInt, which is unpredictable, unlike Math.random.

  2. Frontendpages/OfferReservationsPage.jsx:50 confirmPickup

    Donor types the code (auto-uppercased) and submits.

  3. Backendcontrollers/reservations.js:111 confirmPickup

    changeReservation (82) locks offer then reservation. Must be the offer's donor (403), code must match ignoring case (400), must be pending and within the pickup window (409). Sets collected.

Cancel a reservation

POST /api/reservations/:id/cancel
  1. Frontendpages/MyReservationsPage.jsx:47 cancelReservation

    Calls the API and reloads the list.

  2. Backendcontrollers/reservations.js:94 cancelReservation

    Only your own (403), only pending and before the deadline (409). Status → cancelled, portions given back to the offer, in one transaction. Cancelling twice is harmless (returns the same result).

Report an offer

  1. Frontendpages/OfferDetailPage.jsx:73 reportOffer

  2. Backendcontrollers/reports.js:8 createReport

    Reason 1–2000 chars, no other fields. INSERT INTO reports … SELECT $1, id, $2 FROM offers WHERE id = $3: no row inserted means the offer doesn't exist → 404.

Admin moderation

Validation & error handling

everywhere
  1. Backendutils/validation.js · utils/httpError.js:6

    Controllers call httpError(400, 'Invalid title.'), which throws. Express 5 catches errors thrown in async handlers automatically.

  2. Backendapp.js:55 error handler

    Bad JSON → 400, too large → 413, our own 4xx → that status + message, anything else → logged, generic 500 (no stack trace to the user).

  3. Frontendservices/api.js:40 request · ui/Alert.jsx

    Non-OK responses become ApiError(message, status); pages catch it and show an Alert. Network failures show "Unable to reach ShareAPlate".

Rate limiting & security headers

middleware
  1. Backendmiddleware/security.js:25 rateLimit

    A Map of ip → { count, resetAt }. Over the max → 429 with Retry-After. Old entries are pruned.

  2. Backendapp.js:25–30

    1000 requests / 15 min for /api; 20 / 15 min for login and register.

  3. Backendmiddleware/security.js:4 securityHeaders

    CSP default-src 'self', frame-ancestors 'none', X-Frame-Options: DENY, nosniff, no-referrer, Permissions-Policy, HSTS. app.disable('x-powered-by').

Design decisions

Why we did it this way

PostgreSQL, not MongoDB

Our data is relational (users → offers → reservations). We need foreign keys, CHECK constraints and transactions with row locks for safe reservations.

Raw SQL with pg, not an ORM

Every query is visible and easy to explain; parameterised queries give the same SQL-injection protection; fewer layers for a project this size.

JWT, not server sessions

Stateless: no session store; works the same in dev (two servers) and production. Short expiry (1 h) limits damage if one leaks. Role is re-read from the DB on each request.

Token in a header, not a cookie

Browsers never attach headers automatically, so CSRF attacks don't apply. Trade-off: JavaScript can read sessionStorage, so we rely on React escaping + CSP against XSS.

routes → controllers → utils

Separation of concerns: routes say who can call what; controllers hold business rules; utils are reusable checks. Easy to find and test.

Soft delete

Offers are marked removed, not deleted, so reservation and report history stays consistent (foreign keys don't cascade).

Short human-friendly pickup codes

6 characters is easy to read aloud; look-alike characters removed; generated with crypto. Only the owning donor can submit one, so guessing isn't practical.

One service in production

Express serves the built site and the API: one URL, no CORS, one thing to deploy.

Server is the source of truth

The frontend hides buttons for convenience; every rule (role, owner, quantity, times) is enforced again on the server, and again by DB constraints.

Vite + plain CSS

Fast dev server, simple build; CSS variables give a consistent design without a UI library to learn.

EasyWhat's the difference between 400, 401, 403, 404, 409?

400 your input is invalid · 401 we don't know who you are (no/bad token) · 403 we know who you are but you're not allowed · 404 doesn't exist · 409 valid request that conflicts with current state (not enough portions, already reserved). Also 413 body too large, 429 too many requests.

Express: headers → JSON parse → rate limit. 3. authenticate verifies JWT, loads user. 4. authorize('recipient'). 5. validateIdParam checks 5. 6. createReservation: validate quantity → transaction → lock offer row → checks → INSERT with random code → decrement portions → COMMIT. 7. 201 JSON → React stores the reservation in state and shows the code.

HardHow do errors thrown inside async controllers reach your error handler?

Express 5 automatically catches rejected promises from async handlers and forwards them to the error middleware (Express 4 needed try/catch or a wrapper). Our httpError throws an Error with a status; the handler at app.js:55 turns 4xx into { error: message } and everything else into a generic 500.

Runs validateIdParam once for any route in that router with :id, before the handler. It rejects anything that isn't a positive integer within PostgreSQL's INTEGER range → 400. So controllers can trust req.params.id.

EasyWhy PostgreSQL?

Relational data with foreign keys, CHECK constraints, unique indexes and ACID transactions with row locking, all needed for safe reservations.

HardHow do you prevent two people from reserving the last portion?

A transaction with SELECT … FOR UPDATE on the offer row. The second request blocks until the first commits, then reads the updated remaining_quantity and gets 409. A CHECK constraint keeps remaining_quantity ≥ 0 as a backup.

HardWhat is a deadlock and how do you avoid it?

Two transactions each holding a lock the other needs. We always lock the offer first, then the reservation, in every function (changeOffer, changeReservation, createReservation), so they can't wait on each other in a cycle.

EasyWhat is a transaction?

A group of queries that all succeed (COMMIT) or all get undone (ROLLBACK). Reserving = insert reservation + decrease portions: both or neither.

EasyWhat is a foreign key? Give an example.

A column that must match a row in another table. offers.donor_id REFERENCES users(id): an offer can't point to a user that doesn't exist, and the user can't be deleted while offers point to them.

HardWhat does the partial unique index on reservations do?

UNIQUE (offer_id, recipient_id) WHERE status = 'reserved': at most one pending reservation per person per offer, but you can reserve again after cancelling. The API checks too; the index guarantees it even under races.

Migrations: ordered SQL files applied once and recorded in schema_migrations. Seed: script that creates demo accounts and offers from .env.

HardWhy store area and category in lowercase?

So filters match regardless of case ("Bakery" = "bakery"), and the index works with a simple equality. The API lowercases (cleanOfferData); the DB CHECK rejects non-lowercase values.

HardHow do you mark reservations "expired" without a background job?

It's computed when reading: CASE WHEN r.status = 'reserved' AND o.pickup_deadline <= now() THEN 'expired' ELSE r.status END. Writes also check the deadline (can't cancel/confirm late). No cron job needed.

HardWhat's the downside of LIMIT/OFFSET pagination?

Large offsets get slower and rows can shift between pages if new items arrive. Fine at our size; keyset pagination (WHERE created_at < last_seen) scales better.

EasyHow are passwords stored?

As bcrypt hashes with cost 12 (bcrypt adds a random salt automatically). We never store or log the plain password. Login uses bcrypt.compare.

controllers/auth.js:11, 34, 67
HardWhy bcrypt and not SHA-256?

SHA-256 is designed to be fast: billions of guesses per second on a GPU. bcrypt is deliberately slow and tunable (cost factor), and salted so identical passwords have different hashes and rainbow tables don't work. It reads only 72 bytes, which is why we cap passwords at 72 bytes.

EasyWhat's inside your JWT?

Header (alg HS256), payload with sub (user id), iat and exp (1 hour), and a signature. No password, no role. Anyone can read a JWT (base64), but can't change it without the secret.

controllers/auth.js:24
HardWhy load the user from the DB on every request instead of trusting the token?

Role changes and deleted accounts take effect immediately, and the token carries nothing worth tampering with. Cost: one indexed primary-key query per request.

sessionStorage: survives refresh, cleared when the tab closes. localStorage would persist forever (bigger risk). An httpOnly cookie hides it from JS but needs CSRF protection. We chose the header approach for simplicity and CSRF immunity, and defend against XSS with React + CSP.

EasyWhat is Vite?

The build tool: fast dev server with hot reload and a proxy; vite build bundles and minifies React into frontend/dist.

EasyHow do you prevent SQL injection?

Parameterised queries: pool.query('… WHERE id = $1', [id]). The value is sent separately and is never parsed as SQL.

EasyHow do you prevent XSS?

React escapes everything in {}; we never use dangerouslySetInnerHTML; CSP blocks outside and inline scripts. A frontend test proves HTML in a title renders as text.

HardWhat is CSRF and why aren't you vulnerable?

CSRF tricks a logged-in browser into sending a request to our site, relying on cookies being attached automatically. We authenticate with an Authorization header that only our JavaScript adds, so a forged request from another site arrives unauthenticated → 401.

HardWhat is IDOR and where do you check for it?

Insecure Direct Object Reference: changing an id to access someone else's data. changeOffer (owner or admin), listReservations (offer owner), cancelReservation (recipient), confirmPickup (donor of the offer).

HardWhat does your Content-Security-Policy say?

default-src 'self' (scripts, styles, fonts, fetch only from our origin), img-src 'self' data:, object-src 'none', base-uri 'self', frame-ancestors 'none', form-action 'self'. That's why fonts are bundled instead of loaded from Google.

HardHow does your rate limiter work and what are its weaknesses?

Fixed window per IP stored in a Map: count requests until resetAt, then 429 with Retry-After. Weaknesses: memory-only (resets on restart, doesn't share across servers), per-IP (botnets, shared Wi-Fi). Production fix: Redis-backed store + per-account limits.

HardWhat's trust proxy for?

Behind a hosting proxy, every request seems to come from the proxy's IP. With TRUST_PROXY=1, Express uses the X-Forwarded-For header for req.ip and req.secure, so rate limiting and HSTS work correctly. Only enabled when we know a proxy is there, because the header can be faked otherwise.

In backend/.env locally (git-ignored) and in the host's environment variables in production. .env.example only has placeholders. The server refuses to start with a missing/short JWT_SECRET.

npm run build installs and builds React; npm run start:prod runs migrations and starts Express, which serves frontend/dist plus /api. Hosted PostgreSQL via DATABASE_URL with SSL. Secrets are env vars on the host.

EasyWhat do async/await do?

async functions return a Promise; await pauses that function until a Promise settles, without blocking the server. Errors become exceptions you can catch.

EasyWhat does ... do in { ...current, [name]: value }?

Spread copies all properties of current into a new object; [name] is a computed key that overwrites one field. We create a new object instead of mutating state so React notices the change.

EasyWhat does ?. and ?? mean?

Optional chaining a?.b returns undefined instead of crashing if a is null. Nullish coalescing x ?? y uses y only if x is null/undefined (unlike ||, which also replaces 0 and '').

HardWhy crypto.randomInt instead of Math.random?

Math.random isn't cryptographically secure, so its outputs can be predicted. crypto.randomInt uses the OS's secure random source, so pickup codes can't be guessed from previous ones.

API / REST
The URLs the website can call; REST = resources + HTTP verbs + JSON + status codes.
Middleware
Function that runs before a route and can stop the request.
Controller
The function that does the work for one URL.

Signed token proving who you are; expires in 1 hour.
bcrypt
Slow, salted password hashing.

Queries that all commit or all roll back.

Row lock: others wait until we commit.

SQL that creates tables / script that adds demo data.

Mark as removed instead of deleting, to keep history.

Header telling the browser which sources it may load.

Another site making your browser send a request with your cookies.

Injecting a script into a page other users see.

Max requests per visitor per time window.
