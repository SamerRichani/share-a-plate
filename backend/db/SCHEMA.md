# ShareAPlate database

The four application tables follow the proposal. `schema_migrations` only records which SQL files have run.

## Relationships and fields

- A donor has many offers; an offer has many reservations and reports.
- Each reservation belongs to one recipient; each report belongs to one reporting user.
- `password_hash` replaces plaintext `password`.
- Offers add `area`, `category`, and `pickup_start` for the required filters and collection window.
- Email, area, and category are stored trimmed and lowercase. The API will normalize input; the database rejects unnormalized values.
- Dates use `TIMESTAMPTZ`. `created_at` records creation time.
- Foreign keys do not cascade deletes, preserving linked reservation and report history.

## Finalized rules for the upcoming API

These rules choose simple defaults where the proposal leaves behavior unspecified. Status values and constraints exist now; the API will implement transitions and permissions in later steps.

| Record | Transitions |
| --- | --- |
| Offer | `active → closed` when a donor stops new reservations; `active/closed → removed` when withdrawn or moderated |
| Reservation | `reserved → collected`, `cancelled`, or `expired`; final states cannot transition again |
| Report | `open → resolved` when addressed, or `open → dismissed` when no action is needed |

- Discoverable/reservable offers must be active, have remaining portions, and have a future pickup deadline. Expiry and sold-out availability are derived from these fields, without additional offer statuses.
- Recipients can reserve before or during the collection window. Pickup is confirmed by the owning donor during that window, using the recipient's code.
- Only one pending (`reserved`) reservation per recipient per offer is allowed. After cancellation, the recipient may reserve again if the offer is still available.
- Recipients may cancel before the deadline. Cancellation restores portions once. Collection does not restore portions.
- Closing an offer stops new reservations but honors existing reservations. Removing an offer cancels pending reservations and restores their portions once; collected records remain.
- Uncollected reservations expire after the deadline. They do not make the expired offer available again.
- Quantity edits cannot reduce the total below committed portions (reserved, collected, or expired). Adjust the remaining quantity by the same amount as the total.
- Pickup codes will be randomly generated by the API, unique, and visible only to the recipient and owning donor.
- Only donors create offers, recipients reserve, and administrators moderate. Public registration cannot grant administrator access.
- Reports require an authenticated user and an existing offer.

SQL enforces foreign keys, normalized/unique emails, allowed roles and statuses, positive quantities, remaining-quantity bounds, valid pickup windows, unique pickup codes, and one pending reservation per recipient/offer. Role ownership, time checks, transitions, and stock updates across tables require API authorization and transactions; they are not implemented with triggers.

## Commands

Run from `backend/` after configuring the PostgreSQL environment variables:

```bash
npm run db:migrate
```

The runner applies ordered SQL files in one transaction and records their names. Running it again skips applied files. Run one migration process at a time. Add a new numbered migration for future changes instead of editing an applied file.

To create local demo accounts, set `ADMIN_EMAIL`/`ADMIN_PASSWORD`, `DEMO_DONOR_EMAIL`/`DEMO_DONOR_PASSWORD`, and `DEMO_RECIPIENT_EMAIL`/`DEMO_RECIPIENT_PASSWORD` in your ignored local environment file, then run:

```bash
npm run db:seed
```

Choose distinct emails and set a password for each account. Passwords must be at least 12 characters and at most 72 UTF-8 bytes (bcrypt's limit). Re-running synchronizes each account's password hash with the value in the ignored environment file, but never changes its role. It errors if a configured email already belongs to a different role. Store the passwords in the ignored environment file, not in the tracked example file.

The seed also creates five sample offers for the demo donor with future pickup windows. The offers are labeled as previews, use example pickup locations, and are not real food availability. Re-running the seed does not duplicate existing demo offers. If the previous seed created `community-kitchen@demo.invalid`, its demo offers are moved to the configured demo donor.

SQL schema: [001_initial_schema.sql](migrations/001_initial_schema.sql). Commands: [migrate.js](migrate.js) and [seed.js](seed.js).
